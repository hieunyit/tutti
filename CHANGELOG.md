# Changelog

## Tutti 0.1.0 (unreleased)

First Tutti release (wire-incompatible with upstream Chorus: proto package `tutti`, `/tutti.*` gRPC paths, `tutti:*` Redis keys, `/bin/tutti` binary, changed Postgres migrations; existing Chorus data is not upgraded automatically, see [upgrading from Chorus](./docs/tutti/upgrading-from-chorus.md)): a fork of [Chorus](https://github.com/clyso/chorus) (base commit `8d2237b`) with resilience features ported from [ReplicaT4](https://github.com/barreeeiroo/ReplicaT4). See [docs/tutti](./docs/tutti/configuration.md) and [upgrading from Chorus](./docs/tutti/upgrading-from-chorus.md).

### Security

- Worker: the metrics server (`metrics.port`) no longer serves `net/http/pprof` (`/debug/pprof/`), which was unauthenticated on all interfaces whenever `metrics.enabled` was true. `/metrics`, `/health`, `/ready` and `/version` are unchanged. Profiling is only available through the opt-in `debug.pprofAddr` server (off by default; bind it to `127.0.0.1` or a pod-local address).

### Fixed

- Worker: objects already at the destination are no longer copied again after a restart or a re-created replication. A multipart ETag depends on the part size, and the worker uploaded with 16 MiB parts while the sources used other sizes (15 MiB, ...), so the ETag comparison never matched for large objects and every one was re-copied (small objects were skipped). Now (1) when the source ETag is a multipart ETag `<md5>-N` the worker infers the original part size (whole MiB with `ceil(size/p) == N`, 15 MiB preferred over 16 MiB when both fit) and uploads with it, so the destination ETag equals the source ETag, and (2) every copied object carries the source ETag as user metadata `X-Amz-Meta-Tutti-Src-Etag`; an object whose size and metadata match and whose recorded source ETag equals the current one is skipped even if the ETags differ (`recordSourceETag`, default on). The key is internal: never copied to another storage and ignored in metadata comparison. **One-time cost:** objects copied by earlier versions have a different multipart layout and no marker, so they are copied once more (then they are skipped); optional `trustSameSizeMultipart: true` skips them instead (heuristic, see [configuration](./docs/tutti/configuration.md#skipping-objects-already-copied)).
- Replications: initial replication progress no longer stalls with very large objects. `initBytesDone` now includes the bytes already transferred of copies that are still running (reported by the worker at most once per second per object, absolute per-object values in `p:repl_init_bytes:{id:gen}:prog`, dropped when the object finishes or fails, never double counted), and `initBytesPerSecond` is computed from bytes actually sent in the last 3 minutes instead of completed objects. `POST /replication/activity` in-flight entries gain `bytesDone`; the console shows `Copied X (incl. in progress) · Y MB/s` and a Progress column in the in-progress table. Additive API change.
- Worker: the replication reconciler no longer logs `replication reconciler cycle error ... no user replication policies found` every minute; "no user replications" is treated as nothing to reconcile (and bucket replications are still reconciled in that case). Real errors are still warnings.
- System settings: a partial `PUT /tutti/system-settings` worker body no longer resets `bandwidthLimitBytes` and `bufferBudgetBytes` to 0. Worker numeric fields track presence (absent keeps the stored value, explicit `0` resets to the default or unlimited for bandwidth); `bufferBudgetBytes` below 16 MiB is rejected.

### Added

- Replications: optional `since` cutoff (like rclone `--max-age`): `POST /replication/add` takes `opts.since` (absolute RFC 3339, not in the future, not before 2000) and the initial copy skips source objects last modified before it at listing time (no task, no HEAD, not counted in object/bytes totals, ETA). Live events and diff reports are not filtered; old objects are never deleted at the destination; versioned buckets filter per version. `get`/`list` return `since`. Postgres control plane: migration `0005_replication_since.sql` (nullable `replication_status.since`), projected to the Redis status hash. No update call: delete and recreate to change it. See [API](./docs/tutti/api.md).
- Worker: optional streaming multipart copy engine (`worker.copyEngine: pipeline`, default stays `legacy` because the benchmarks did not show it better than the legacy parallel path) and optional resumable multipart uploads (`worker.resumeMultipart`, off by default, pipeline engine only; read the warning in [configuration](./docs/tutti/configuration.md#copy-engines-resumable-multipart-and-part-sizes)). Part size is now at least `ceil(size / 9000)` MiB-rounded for both engines, so the 10000-part limit cannot be hit. In-process benchmarks with a fake S3 server (latency, per-stream and total bandwidth caps, fault injection) are part of the test suite.

- Worker: orphaned multipart uploads are cleaned up. After a failed or cancelled multipart copy the upload is aborted with a fresh context (1 min, 3 tries), and before a multipart copy of a key the incomplete uploads of that exact key older than 5 minutes are aborted; both only while the destination-key lock is held. `orphanUploadCleanup: false` rolls it back. See [configuration](./docs/tutti/configuration.md#orphaned-multipart-uploads).

- Worker: large-object concurrency cap. Initial-replication and diff-fix copies of objects of 128 MiB or more take a slot of a per-destination-storage limit (new system setting `worker.largeObjectStreams`, `0` = auto: 2 per CPU clamped to 4..16; YAML/env `largeObjectStreams`; API `effective`/`recommended`/`tuningSources`, console field with Auto badge; applies live). Smaller objects and live events are never limited; a copy that finds no free slot is re-queued after 3..10 s without holding a worker slot or counting as a failure. Set a large value to disable. See [configuration](./docs/tutti/configuration.md#large-object-concurrency-cap).

- Worker: optional pprof server for CPU/heap profiles of the real worker. OFF by default; set `debug.pprofAddr` (env `CFG_DEBUG_PPROFADDR`, e.g. `127.0.0.1:6060`) and take a profile with `docker compose exec` / `kubectl port-forward` (see [throughput tuning](./docs/tutti/configuration.md#profiling-the-worker)). 
- Replications: live activity log. New read-only `POST /replication/activity` (`Policy/GetReplicationActivity`, viewer allowed) returns the object copies running now and a capped event log (started, done with duration and speed, retry, failed, skipped) with a cursor for incremental polling. The worker records it in the queue Redis per replication id and generation (event stream about 1000 entries, in-flight set 500 entries with a 2 h safety expiry, best effort, live-event flow sampled to 20 objects/s). The console opens a replication detail view (`/replications/detail?id=...`, click the name) with a console-style tail, and `tuttictl repl logs <id> [-f] [--tail N]` prints it. See [docs/tutti/api.md](docs/tutti/api.md).
- Replications: initial replication progress by bytes. `get`/`list`/stream return `initBytesTotal`, `initBytesDone`, `initBytesPerSecond` (completion-based, rolling 5 minutes), `initEtaSeconds` and `initListingComplete`; the console shows a bar with `12.4 GB / 812 GB (1.5%) · 8.7 MB/s · ~25 h left` and the object count as secondary text (total is "at least" until the listing finishes, ETA unknown without throughput); `tuttictl repl` has an `INIT_BYTES` column. Redis runtime counters, no migration; versioned buckets keep object counts only. See [API](./docs/tutti/api.md).
- Replications: optional display name (max 64 characters, trimmed, no control characters, not unique, not part of the replication id). `POST /replication/add` takes `name`, new `PUT /replication/rename` (admin, audited `RENAME`) changes it without affecting copying or routing; `get`/`list` return it. Postgres control plane: migration `0004_replication_name.sql` (`replication_status.name`, default empty) projected to the Redis status hash; replications without a name keep working. Console: Name field on the add form, name (or `<from> → <to> · <bucket|all buckets>`) as primary text of the list row with inline rename, searchable; `tuttictl repl add --name`, `tuttictl repl rename`, `ID` and `NAME` columns in `tuttictl repl`.
- Worker: hardware-aware tuning. At startup the worker detects the CPU and memory available to the process (cgroup v1/v2 and Kubernetes limits, `GOMAXPROCS`) and derives `concurrency`, `bulkConcurrencyPercent` and `bufferBudgetBytes` for knobs without an explicit value (e.g. 4 CPU / 32 GiB: concurrency 40, 8 GiB buffer; 1 CPU / 1 GiB: unchanged 10 / 256 MiB). `GOMEMLIMIT` is set to 90% of a cgroup memory limit when unset. `concurrency`, `bulkConcurrencyPercent`, `multipartThreads`, `multipartPartSizeMiB` default to `0` (= auto) in `config.yaml` and the Helm chart; `0` is accepted for `concurrency` and `bufferBudgetBytes` in System settings (never unlimited). `GET /tutti/system-settings` returns `hardware`, `recommended`, `effective`, `tuningSources`; the console shows the detected hardware and Auto badges. Existing installations keep their stored `concurrency: 10` / 256 MiB as explicit values until set to `0` (see [configuration](./docs/tutti/configuration.md#hardware-aware-defaults)). `multipartThreads` stays 1 (parallel parts slower in loopback tests).
- Auth: first-run admin password. The generated password is printed once as a banner on stderr instead of a JSON log field; a provided `TUTTI_BOOTSTRAP_ADMIN_PASSWORD` / `bootstrapAdminPassword` must have at least 12 characters (startup fails otherwise); new `chorus admin reset-password [--user] [--password-env]` recovery command that revokes the user's sessions; `docker-compose/.env.example`, Helm `auth.bootstrapAdmin.{existingSecret,forceChange}` and a login page hint. See [First login and password recovery](./docs/tutti/operations.md#first-login-and-password-recovery).
- Worker: `bulkConcurrencyPercent`, `multipartThreads` (optional, default 1; the gain of values above 1 is unverified, measure first) and `multipartPartSizeMib` in System settings (system setting > YAML/env > default; multipart knobs and the buffer budget apply to the next copy without restart). Worker throughput: per-process counters published to Redis every 5 s, `GET /tutti/worker-stats` and Prometheus metrics `tutti_copy_*`.
- Auth: sliding console sessions. A session ends after `api.auth.sessionIdleTimeout` (default 30m) without refresh and never lives past `api.auth.sessionMaxLifetime` (default 24h, replaces `sessionTTL`, which is still read as the max lifetime when the new key is unset). New `POST /auth/refresh` is the only call that extends a session (6 per minute per token, `429` with `Retry-After`; `401` at the cap); ordinary API calls and polling never extend it. Login and `GET /auth/me` return `expiresAt`, `maxExpiresAt` and `serverTime`.
- Storage-level replication: `user` is optional on replications (API, `tuttictl repl`, UI); an empty user copies storage A to B with each storage's connection account. The internal `$service` identity was removed. A shared overlap rule applies to replication add, group create and group update: same destination or reverse direction with intersecting buckets is rejected with HTTP 409 (reason in the error details; `tuttictl` prints it and exits non-zero); replications of the same user (storage-level, or the same real user) with a different source storage on a shared bucket (or both all-buckets) are rejected too, with a distinct reason, because the policy stores keep one source per bucket; same source with different destinations, and chains or unrelated pairs on disjoint buckets are allowed; "all" intersects everything, objects of different real users conflict only on intersecting explicit bucket lists, and storage-level objects cover every bucket of the storage. `list-buckets` also returns `coveredBuckets`. One source to many destinations is several replications or one group. Data behavior: same name with different content is overwritten by the source, destination-only objects are never touched, identical objects are skipped.
- Proxy: decode and verify `aws-chunked` (`STREAMING-*`) payloads before forwarding; `mc`/`minio-go` signed streaming uploads now work. Checks chunk and trailer signatures, `x-amz-checksum-*` and decoded length (`f3b063a`).
- Proxy: optional synchronous replication on the write path (`replication.sync.{enabled,writeQuorum,timeout,onQuorumFailure}`), `X-Tutti-Replicas` response header (`178745f`).
- Proxy: per-storage circuit breakers fed by periodic health probes and real traffic; fail-fast `503` for unavailable storages; `health.{failureThreshold,openDuration}`, `storage.<name>.healthCheckInterval`; metrics `storage_available`, `storage_breaker_transitions_total` (`5949da2`).
- Proxy: optional automatic failover with operator-defined policies and ordered targets (`failover.*`), Redis lock so one proxy acts, failover events, metric `failover_total` (`a5e56fb`).
- API: `Resilience` gRPC/REST service (`/tutti/proxies`, `/tutti/failover/policies`, `/tutti/failover/events`), `tuttictl proxies` and `tuttictl failover policies|events`, proxy status published to Redis (`95084c2`).
- UI: Tutti branding, Storage health (`/health`) and Failover (`/failover`) pages (`5be1f60`).
- Tests and CI: resilience e2e suite against MinIO (`test/resilience`), `go test -race` unit job, UI job (`1ca8525`).

### Changed

- `Content-Type` no longer has to be signed in SigV4 requests; `auth.requireSignedContentType: true` restores the strict check. `host` and `x-amz-*` must still be signed (`96d3046`).
- Replication event recording is retried (`replication.eventRetryBudget`, default 2 s); if it still fails the proxy answers `503` instead of a silent success (`replication.onEventError: fail`, default; `log` restores old behavior) (`96d3046`).
- Requests only carry replications whose source is the storage the request was routed to, so a failed-over scope does not record events against the failed storage (`90917fc`).
- Rename: Go module `github.com/hieunyit/tutti`; protobuf package and service names unchanged (`ab97996`).

### Fixed

- Data races in standalone startup and shared globals (`features`, logger) (`f76ce1f`).
- Data race in `pkg/objstore` credentials sync (`1ca8525`).

### Known limitations

- No automatic failback; see [manual failback](./docs/tutti/operations.md#manual-failback).
- Failover policies cannot be set with `tuttictl`; use REST/gRPC or the UI.
- Swift storages are not health-probed.
